# ADR-0011: Use the dbt semantic layer in both reference implementations

**Status:** accepted. **Date:** 2026-10-15.

## Context

The semantic layer is the one place indicators are defined
([P11](../principles.md#p11-reporting-goes-through-a-governed-transformation-layer)).
The two reference implementations serve different consumers: open-source
dashboards on one, managed dashboards and natural-language query on the
other. If each implementation defined measures in its own tool, the same
indicator would be written twice and could differ.

As of October 2026: dbt's semantic definitions are written in YAML beside
the dbt models; MetricFlow, which validates and compiles them, is
Apache-2.0 licensed and has SQL dialects for both Trino and Databricks;
Databricks metric views can be created by dbt-databricks through its
`metric_view` materialisation; and an open interchange format for semantic
definitions (Apache Ossie) exists but is still in incubation.

## Decision

- Measures and indicators are written once, in dbt's latest semantic YAML
  specification, in the same project as the transformation models.
- Both implementations compile them with MetricFlow. Serving artefacts are
  generated by CI from the semantic manifest: Unity Catalog metric views on
  Databricks, and saved-query tables on both.
- Definitions stay within a portable subset (simple, ratio, and derived
  without time offsets), with every indicator a ratio of additive counts on
  one gold table.
- A parity test runs every saved query through every serving path and
  requires identical results.
- Neither implementation depends on dbt's hosted platform; its APIs may be
  added where an operator chooses, but nothing in the blueprint requires
  them.
- Apache Ossie is tracked, and replaces the generators once a released
  version is supported by both dbt and the consuming engines.

## Consequences

- One definition, many consumers; a change to an indicator is one reviewed
  change.
- The generators are small pieces of code the implementations own and test.
- Without the hosted platform, ad-hoc metric queries on the open-source
  stack come from a thin MetricFlow-backed service rather than a managed
  API; dashboards read generated tables until Superset's semantic-layer
  support is mature.
- The portable subset rules out some metric types for published
  indicators; any exception needs a recorded mapping per engine.
